# license-verify · v1

> **变更块**
> - 2026-11-01 v1 首次落地。起因：一张证载"有效期至 2025-05-27"的食品经营许可证，
>   在 2026 年 10 月的核验任务中被模型判为"合格"。模型没有"今天是哪天"的概念。
> - 该事故的修法从三个方向同时下手：本模板（提示词禁令）+ 输入补 `verificationDate` 参数
>   + 代码层正则抽日期强制兜底。**只改提示词是不够的**，这一条写在下面第 3 节。

---

## 1. 目标

判断一份许可证在**指定的核验日期**当天，是否仍在有效期内、经营范围是否覆盖被检查事项。

只做这两件事，不做主体归属性判断，不做真伪判断。

## 2. 范围

- 有效期判断只用两个值：证面载明的有效期截止日期，与输入中给定的 `verificationDate`。
- 经营范围判断只比对证面载明的经营范围文字与被检查事项的名称。**名称不完全一致但有包含关系时，返回 `UNKNOWN`，不要自行等同。**
- 主体名称、信用代码的归属校验**不在本模板范围内**（需要业务系统提供对照数据，缺数据时输出 `UNKNOWN`）。

## 3. 禁止动作

1. **禁止**使用图片拍摄时间、发证日期、系统调用时间、训练数据中的时间，作为"今天"的替代。
   **判断"是否过期"只能以 `verificationDate` 为基准。** 如果 `verificationDate` 缺失，直接返回 `UNKNOWN`，不要猜。
2. **禁止**在证面没有清晰载明有效期时，按行业惯例推定有效期年限（例如"食品经营许可证一般五年"）。
3. **禁止**把"发证日期 + 常见有效期"推算出的截止日期当作证载事实写进 `evidence`。
4. **禁止**在 `evidence` 中写你自己组织过的句子。必须是证面原文的逐字片段。
5. **禁止**输出 `PASS` 时不给 `evidence`。
6. **禁止**给出"基本符合""大致有效""应该没问题"这类模糊结论。

## 4. 输出格式

```json
{
  "validOnVerificationDate": "PASS | FAIL | UNKNOWN",
  "expiryDate": "YYYY-MM-DD 或空字符串",
  "verificationDate": "必须原样回填输入中的值",
  "evidence": "证面原文逐字片段",
  "scopeCovered": "PASS | FAIL | UNKNOWN",
  "missingEvidence": "UNKNOWN 时说明缺什么",
  "confidence": 0.0
}
```

关键约束：

- `verificationDate` **必须原样回填**。这是为了让下游能核对"模型到底拿哪天做的判断"，
  也是这个模板最重要的一条自证机制。
- `expiryDate` 只能来自证面，抽不出来就留空并返回 `UNKNOWN`，不要推算。

## 5. 验收标准

| 校验 | 不通过时的原因码 |
|---|---|
| `verificationDate` 非空且与输入一致 | 调用层直接拒绝，不进入模型 |
| `evidence` 逐字出现在 OCR 原文中 | `E_EVIDENCE_NOT_FOUND` |
| `evidence` 长度 ≥ 4 | `E_EVIDENCE_TOO_SHORT` |
| `PASS`/`FAIL` 的 `confidence` ≥ 0.90 | `E_LOW_CONFIDENCE` |
| 未对禁止项下结论 | `E_FORBIDDEN_ITEM` |

## 附一：代码层兜底规则（提示词之外的第二道）

提示词禁令能降低错误率，但不能把错误率降到零。**关键合规判断必须有一道不依赖模型的硬判规则。**

兜底逻辑（从 OCR 原文里正则抽 `有效期至|截止日期|到期日期` 后面的日期）：

**四个条件同时成立才触发强制判否：**

1. 文档类型是食品经营许可证（不是所有证都适用这条规则）
2. OCR 的 `warnings` 中没有提到日期相关的识别问题（识别不可靠时不硬判）
3. 抽出的日期唯一，且不含冲突
4. 该日期不是发证日期

触发后：若 `expiryDate < verificationDate`，**直接覆盖模型结论为 FAIL**，并在返回里标注 `overriddenBy=RULE`。

**为什么条件要写得这么窄：**

> 宁可漏兜，不可误杀。冤枉一家合规的店，比漏判一家过期的店，后果严重得多。
> 硬判规则出错的方向必须是"判不了"，不能是"判错了"。
