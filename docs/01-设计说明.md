# 01 · 设计说明：为什么"门禁"比"更好的提示词"重要

## 一、这个项目在解决什么问题

一句实话：**AI 生成的业务代码，"能不能跑"和"能不能上线"之间，差一整套判定规则。**

现实里的失败长这样（都是真实发生过的，见 `prompts/failure-cases.md`）：

- 接口 200 正常返回，12 项结论里有 8 项，剩下 4 项没写——系统以为"这批就 8 项"。
- 结论是对的，但证据是编的——现场记录里没有那句话，模型为了自洽补了一句。
- 置信度 0.71，但 `result` 填了 `PASS`——模型知道自己不确定，输出里却看不出来。
- 请求清单里没有 `9.9` 这一项，模型返回了 `9.9`，内容还挺像。

这些问题有个共同点：**没有一条会抛异常。**

所以防不住的方式也很统一：`try { parse } catch { log }` 之后照常落库。真正的脏数据不是"报错的数据"，是"看起来正常的数据"。

门禁就是把这些"看起来正常"的判定，变成**显式的、可测的、带原因码的拒绝**。

---

## 二、三条原则（顺序不能反）

### 原则 1：技术故障整包拒绝

截断、空输出、结构非法——这类问题下的每一个字段都可能不可信，逐项挑也没意义。**整包拒绝，让上游重试或降级。**

判据：`finish_reason != "stop"`，或结论数组为空。

### 原则 2：业务不确定逐项拒绝

缺项、证据不足、置信度低——这些是"这一项判不了"，不是"这一批坏了"。**其余项照常交付，只标记 `incomplete`。**

这条是整套设计的价值所在。反面案例就是最常见的写法：

```
任一项判断不了 → 抛 422 → 整批不可用
```

结果是：12 项里有 1 项 OCR 质量差，另外 11 项全部白干。真实业务里的可用率会被这一条打到地板。

**正确的做法是把两种失败分开：业务不确定返回 200 + 逐项业务码，只有技术故障才算异常。** 这一条在这个项目里体现为 `Response.rejectedAll` 与 `Response.incomplete` 两个独立布尔位。

### 原则 3：冲突整项丢弃，不择一

同一个 `itemId` 返回两条矛盾结论时，**不取最新、不取置信度高、不取证据长的**。

理由很直接：两条都自称有证据、置信度都在 0.95 以上时，选哪条都是赌博。代码替人做的这个决定，出了事没人担得起。

**这种情况下正确的动作是交给人，不是让机器更聪明一点。**

## 三、八条规则

| 编号 | 规则 | 拦住什么 | 原因码 | 作用层 |
|---|---|---|---|---|
| G0 | `finish_reason` 必须为 `stop` | 截断但 JSON 可解析 | `E_TRUNCATED` | 整包 |
| G1 | `itemId` 必须在请求清单内 | 编造、串项 | `E_ITEM_NOT_REQUESTED` | 单项 |
| G2 | `result` 必须是四枚举之一 | 自由文本结论 | `E_RESULT_NOT_ENUM` | 单项 |
| G3 | `PASS/FAIL` 的 `confidence ≥ 0.90`，且与结论不矛盾 | 低置信度硬判、说着不知道却极度自信 | `E_LOW_CONFIDENCE`、`E_CONF_CONFLICT` | 单项 |
| G4 | `evidence` 必须逐字出现在原文中且 ≥ 4 字 | 证据幻觉 | `E_EVIDENCE_NOT_FOUND`、`E_EVIDENCE_TOO_SHORT` | 单项 |
| G5 | 每个请求项都必须有结论 | 静默丢项 | `E_ITEM_MISSING` | 整批标记 |
| G6 | 同项结论必须一致，否则整项丢弃 | 矛盾输出被静默覆盖 | `E_CONFLICT` | 单项 |
| G7 | 禁判项的模型结论一律不采用 | 越权下结论 | `E_FORBIDDEN_ITEM` | 单项 |

### 每条规则的取舍，逐条说清

**G0 为什么排第一**：因为它是唯一一条"不校验内容只校验完整性"的规则，也最容易被漏掉。只要 JSON 能 parse 就放行，等于把最危险的一类错误直接放过去。

**G1 为什么用白名单而不是黑名单**：黑名单永远列不全。清单外的一切都拒绝，规则才封闭。

**G2 为什么枚举校验要放在置信度之前**：`result = "基本合格"` 的时候，置信度是 0.99 还是 0.5 都不重要，字段本身不可用。校验顺序应该按"错误的严重度"排，不是按代码书写顺序排。

**G3 为什么 `UNKNOWN` / `NA` 豁免置信度和证据**：这两个值的语义就是"判不了""不适用"。如果对它们也要求证据和置信度，结果是**模型诚实地说"我不确定"反而被门禁打死**，训练它去编一个 `PASS`。这是最反直觉、也最容易写错的一条。

**G3 的附加规则：`UNKNOWN` + 置信度 ≥ 0.95 判矛盾**。"极度确信自己不知道"是模型措辞漂移的典型症状，这种输出通常意味着它在两个答案之间摇摆，两个都不可信。

**G4 为什么只做格式归一化，不做模糊匹配**：归一化覆盖空白、全角、大小写——这些是"同一个人写两遍"的正常差异。同义词、编辑距离、部分匹配一律不做，因为**放过一条编造的证据，整批结论的可信度归零**。宁可漏判（人可以补），不可误放（没人会回头查）。

**G4 为什么有最短长度**：`"是"`、`"无"`、`"通过"` 这些都能在原文里找到，但它们不构成证据。4 个字是个经验值，也是能被业务方接受的最低限度。

**G5 为什么不补一个"合理缺项"**：补了，就永远发现不了模型在丢项。缺项必须显式暴露成 `incomplete`，让上游和监控看到。

**G6 的"整项丢弃"是有代价的**：本来能得到 1 条结论，现在 0 条。但这个代价值得——因为它把"静默覆盖"变成了"明确告警"。**能被看见的失败，比被掩盖的成功有价值。**

**G7 为什么必须在代码层拦，不能只写提示词**：约束在提示词里的遵守率永远不是 100%。凡是"不许模型做的事"，都得有代码兜底。提示词降低概率，代码保证下限。

## 四、阈值是怎么定的

| 参数 | 值 | 依据 |
|---|---|---|
| `MIN_CONFIDENCE` | 0.90 | 这是**结论性**输出（`PASS`/`FAIL` 直接影响执法判定）。低于 0.90 的结论宁可转人工。如果只做辅助提示，可以降到 0.75——**阈值应该跟着后果走，不是跟着感觉走** |
| `MIN_EVIDENCE_LEN` | 4 | 3 个字以内基本是语气词或单字判断，无法定位到原文位置 |
| 矛盾判定线 | 0.95 | `UNKNOWN` 且置信度极高，属于输出自相矛盾。取 0.95 是为了不误伤"真的很有把握地说'这项不适用'"的场景 |

**这三个数字都可以通过构造函数覆盖**（`new Engine(minConfidence, minEvidenceLen)`），但默认值必须保守——**默认值宽松的系统，实际运行中永远不会有人去调紧。**

## 五、明确不做的事

写清楚边界比写清楚功能更重要。这个项目**不做**以下四件事：

1. **不做模型路由**。小模型/大模型分级是调用层的事，门禁只判定"这次输出能不能用"。混在一起会让责任边界模糊。
2. **不做 RAG**。知识库检索的召回质量是另一个问题域，跟"输出是否可信"正交。硬塞进来只会让两边都做不好。
3. **不做自动修正**。门禁只负责**拒绝并说明原因**，不负责"猜一个正确的值填上去"。任何自动修正都是在脏数据上盖一层更干净的脏数据。
4. **不宣称提升准确率**。门禁提升的是**可用数据的可信度**，代价是**可用数量下降**。这两个指标必须一起看，只看一个必然自欺。

---

## 六、这套东西的边界（面试时主动说）

**它解决的是"AI 输出的形式与自洽性"，不解决"AI 的判断是否正确"。**

一个证据真实、置信度高、格式完全合规的 `PASS`，仍然可能是错的——只是错得"很干净"。

要解决判断正确性，需要的是**评测集**：100–200 个人工标注的真实样本，跑批量算准确率。

**这个项目没有做评测集。** 这是明确的欠账，不是设计选择。理由是：标注成本高，且需要业务方参与定义"什么算对"。但这不影响门禁本身的价值——门禁和评测是两件事，前者管"能不能用"，后者管"准不准"。

**主动说出这个边界，比藏起来可信得多。**
