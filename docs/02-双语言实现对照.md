# 02 · 双语言实现对照：把同一套规则写两遍，是为了证明什么

## 一、为什么要写两遍

不是为了"多一门语言"。是为了回答 JD 里那句具体的要求：

> 能在 1–2 天内通过 AI 辅助上手一门新语言或新框架，并达到**准生产级别的交付质量**。

这句话的重点不是"上手"，是"准生产级别"。而"准生产级别"没法自证，只能用一个**已知正确的参照物**来对齐。

所以这里的做法是：

1. 先用 Java 实现完整的 8 条规则 + 17 条断言（Java 是有底子的那门，作为**语义基准**）。
2. 再用 Go 实现同一套规则，**不改任何一条规则的语义，只改表达方式**。
3. 两边跑同一批断言，**逐条对比输出**。输出不一致，就是迁移出错，不是"语言差异"。

**这个方法的可验证性在于：它有一个明确的成败判据。** "我学会了 Go"是无法被检验的声明；"同一批 17 条断言，两种语言的输出逐字节一致"是可以被检验的事实。

## 二、Java 与 Go 的真实差异（都是踩出来的，不是查来的）

下面每一条，都会导致"代码能编译、行为不一样"。这类问题比编译错误危险得多。

### 1. 空白的定义不一样 —— 最容易翻车的一条

```java
// Java：这是错的
Character.isWhitespace('\u3000')  // → false
```

全角空格 `U+3000` 在 Java 里属于 `SPACE_SEPARATOR`，**不是** `WHITESPACE`。只写 `isWhitespace` 会漏掉它。

而 Go 的 `unicode.IsSpace` **包含** `U+3000`。所以从 Go 迁 Java 时，这一行会被原样翻译，然后：

> 测试用例「全角空格与全角标点归一化后仍算命中」直接失败。

更麻烦的是：**如果测试用例里没有这条全角空格用例，这个 bug 会一直活到线上**——因为它在绝大多数输入下都正常，只在用户输入法切到全角时出问题。

```java
// 正确写法
if (Character.isWhitespace(c) || Character.isSpaceChar(c)) continue;
```

```go
// Go 侧一行就够
if unicode.IsSpace(r) { continue }
```

**结论：跨语言迁移时，最危险的不是语法，是"名字一样但语义差一点"的标准库函数。**

### 2. 长度的定义不一样

| 语言 | 写法 | 单位 |
|---|---|---|
| Java | `s.length()` | UTF-16 code unit |
| Go | `len(s)` | byte |
| 正确姿势 | Java `s.codePointCount(0, s.length())` / Go `len([]rune(s))` | Unicode 码点 |

中文都在 BMP 内，三者结果相同；但一个 emoji 在 Java 是 2、在 Go 是 4、按码点才是 1。

这个项目里它影响 `evidence` 的最短长度判断——**如果业务里出现 emoji 或生僻字（`𠮷` 这类扩展 B 区汉字），只写 `length` 会出现"3 个字的证据被判成 4 个字"或反之。**

### 3. 不可变语义的来源不一样

```java
public record Verdict(String itemId, String result, String evidence, double confidence) {}
```

`record` 从语言层面保证不可变。Go 没有对等物：

```go
type Verdict struct {
    ItemID     string  `json:"itemId"`
    Result     string  `json:"result"`
    Evidence   string  `json:"evidence"`
    Confidence float64 `json:"confidence"`
}
```

而且字段**必须是导出的**（首字母大写）才能被 `encoding/json` 序列化。所以 Go 里的"不可变"只能靠约定：**函数接收值而不是指针，需要修改时返回新值。**

这不是妥协，是语言设计取向：Go 用"复制"控制可变性，Java 用"类型"控制。

### 4. 字段名的坑：忘了 tag，前端直接坏

```go
ItemID string `json:"itemId"`   // 没有这个 tag，序列化出去是 "ItemID"
```

Go 的默认行为是按字段名原样输出。`ItemID` 会变成 `"ItemID"`，而契约要求 `"itemId"`。大小写不一致，前端 `data.itemId` 直接 `undefined`。

**这类错误编译期完全发现不了，只有联调时才炸。** 而 Java 用 record 时字段名就是访问器名，天然不会有这个问题——所以从 Java 迁 Go 时，这是最容易漏的一步。

### 5. 空值处理的方向相反

| | Java | Go |
|---|---|---|
| 列表为空 | `null` → `for` 循环 NPE | `nil` slice → `range` 安全，长度 0 |
| 写入空 map | 不会发生（用 `HashMap`） | `nil` map 写入 **panic** |
| 缺省数值 | `double` 字段不存在时是 `0.0` | 同 |

Go 的 `nil slice` 能安全遍历，导致**"请求没传结论列表"和"传了空列表"行为一样**。在这里没问题（G0 之后都会判空），但如果哪天真要区分这两件事，就会踩到。

而对 `nil map` 写入直接 panic —— 这是 Go 里最经典的运行时事故之一，而且往往在"看起来不可能为空"的地方发生。

### 6. 异常 vs 返回值：别直译

Java 用 `throw new JsonException(...)`，调用层 `catch`。Go 用 `(value, error)`。

**反模式（AI 最爱写）：** 把 Java 的 `try-catch` 直译成 Go 的 `panic/recover`。

```go
// 错
defer func() {
    if r := recover(); r != nil { log.Println(r) }
}()
```

`panic` 是"程序有 bug"，不是"输入有问题"。用 panic 处理可预期的输入错误，会让调用方无法用 `if err != nil` 正常分支，也会让 goroutine 泄漏排查变得极其困难。

**这个项目里 Go 版没有手写 JSON parser，正是因为这个：** `encoding/json.Unmarshal` 用 `error` 返回，`io.ErrUnexpectedEOF` 天然能表达"输入提前结束"。不需要为了统一而硬造一个 panic 版本。

### 7. 并发模型：同一条代码，吞吐差一个数量级

```go
// Go：每个请求一个 goroutine，天然并发
srv := &http.Server{Addr: addr, Handler: mux}
srv.ListenAndServe()
```

```java
// Java：HttpServer 的 executor 默认是 null
HttpServer server = HttpServer.create(addr, 0);
server.setExecutor(Executors.newFixedThreadPool(n));  // 这一行不写，就是串行
```

`com.sun.net.httpserver.HttpServer` 不设 executor 时，处理是**串行**的。而 Go 的 `net/http` 每个连接一个 goroutine。

**这是"能跑"和"能上线"的分界线**：功能测试全过，压测 QPS 卡在个位数。

（要说明的是：Java 生态里正经做 Web 不会用 `com.sun.net.httpserver`，会用 Spring Boot / Netty。这里用它只是为了零依赖、能一条命令跑起来。但"默认值决定性能"这个知识点是真的。）

### 8. 两侧的取舍清单

| 维度 | Java 版 | Go 版 | 为什么不一样 |
|---|---|---|---|
| JSON | 自写 180 行 parser | `encoding/json` | Java 侧需要精确的截断位置；Go 的 err 已足够 |
| HTTP | `com.sun.net.httpserver` | `net/http` | 都是零依赖，只是各自的"内置"不同 |
| 依赖 | 0（`javac` 一条命令） | 0（`go run .` 一条命令） | 刻意：面试时不能等下载 |
| 测试 | 自写断言 + 通过计数 | `go test` 表驱动 | `go test` 是原生的，没必要自造 |
| 端口 | 8091 | 8090 | 便于同时起、直接对比 |

## 三、怎么证明两边真的等价

不是"看起来一样"，是**同一批输入、同一批期望、逐条核对**。

```bash
# Go
cd guard-go && go test ./... -v

# Java
cd guard-java && run.bat
```

两边的用例名**故意写成一样的**（`输出被截断时整包拒绝`、`证据是编造的要判死`……），这样输出可以直接肉眼对齐。

当前状态：

- Go：18 条用例（`TestCheck` 17 子用例 + `TestStatsConsistency` + `TestOutOfScopeCountedSeparately` + `TestCheckNil` + `TestNormalize`）全过
- Java：17 条用例全过
- 两边 `demo` 的 JSON 输出**逐字段一致**

**"逐字段一致"这句话是可以当场验证的**：同时起两个服务，`curl 127.0.0.1:8090/demo` 和 `curl 127.0.0.1:8091/demo`，diff 一下。

## 四、这套方法可以复用到任何语言

迁移任何"规则型"代码，都用这四步：

1. **先固定语义基准**——在最有把握的语言里写完整实现 + 断言集。断言是唯一的真相来源。
2. **迁移时只读断言，不读原实现**。读原实现会不自觉地把语言 A 的写法套到语言 B 上，这是 90% 迁移 bug 的来源。
3. **先让断言全红，再让它们全绿**。跳过中间态，否则你不知道自己是不是"改断言让它变绿"。
4. **逐条核对差异，不接受"结果差不多"**。规则型代码没有"差不多"，只有"等价"和"不等价"。

第 2 步最反直觉，也最有用：**读断言的人会问"这条规则在说什么是错的"，读原实现的人只会问"这行代码怎么翻译"。**
